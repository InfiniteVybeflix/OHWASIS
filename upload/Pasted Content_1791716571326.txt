6. Product architecture and tenant boundaries

OHWASIS must support many independent businesses using a shared platform.

The architecture should distinguish three product layers.

A. Platform operating system

The platform operator manages the overall service, merchant onboarding, platform settings, approved integrations, support operations, platform security, and platform-wide health.

B. Merchant operating system

Each merchant has an independent control panel for their storefront, products, orders, customers, payment configuration, delivery rules, branding, content, AI settings, staff, and business settings.

C. Customer commerce experience

Customers can discover businesses, browse available products, create carts, check out, select supported payment methods, track orders, and manage their own accounts where applicable.

Keep these layers distinct while sharing reusable services and carefully scoped data models.

Required tenant isolation

Use Supabase PostgreSQL as the primary database unless documented research identifies a compelling, technically necessary alternative.

Design tenant isolation from the beginning. Do not bolt it on after building a single-merchant application.

Consider a shared database with explicit tenant ownership, composite constraints where appropriate, and PostgreSQL RLS.

Implement all necessary controls:

- Every tenant-owned record must have an enforceable tenant relationship.
- Related records must not be attachable to another tenant through manipulated IDs.
- Establish trusted tenant context on the server.
- Resolve storefront tenants using a verified hostname or authenticated membership as appropriate.
- Never trust a client-provided "tenant_id" as sufficient authorization.
- Enforce authorization in database policies and server-side application logic.
- Prevent cross-tenant access through APIs, direct database access, joins, nested queries, search, exports, analytics, and file downloads.
- Scope background jobs, scheduled tasks, webhooks, caches, and asynchronous processing correctly.
- Prevent tenant data from leaking through error messages, logs, notifications, AI prompts, and shared caches.
- Restrict platform-level cross-tenant access to explicitly authorized, audited operations.
- Ensure database connection pooling and transaction-local tenant context cannot leak between requests.
- Ensure privileged service-role access is never exposed to browsers and cannot silently bypass application authorization.
- Restrict database functions and views appropriately.
- Use foreign keys, indexes, transactions, and constraints to enforce integrity.

Test attacks that deliberately substitute another tenant's IDs in requests, URLs, form fields, nested objects, uploads, exports, and API calls.

A merchant must never be able to read or modify another merchant's products, customers, orders, payments, integrations, private media, credentials, staff, or analytics.

A customer must never access another customer's private order or account information.

21. Security verification and vulnerability assessment

Perform a genuine security assessment throughout development and again before final packaging.

Do not simply write “secure” in the README.

Authentication and authorization

Test:

- Unauthenticated access to protected endpoints.
- Invalid and expired sessions.
- Role escalation.
- Cross-tenant object access.
- Customer access to other customers' records.
- Unauthorized administrative operations.
- Disabled-account access.
- Password recovery and session revocation.
- Sensitive route and API discovery.
- Rate limiting and abuse resistance.

Database and Supabase

Test:

- RLS on every applicable tenant-owned table.
- Anonymous and authenticated database access.
- Cross-tenant SELECT, INSERT, UPDATE, and DELETE attempts.
- Privileged server access and service-role boundaries.
- Storage object policies.
- SQL injection and unsafe dynamic queries.
- Database functions and views.
- Referential integrity and concurrent updates.
- Tenant context under connection pooling.

Application and API security

Assess:

- Injection and unsafe input handling.
- XSS and content sanitization.
- CSRF where applicable.
- SSRF risks.
- Open redirects.
- Path traversal.
- File upload abuse.
- Broken object-level authorization.
- Sensitive information exposure.
- Insecure caching.
- Weak cryptography.
- Dependency vulnerabilities.
- Security headers and CSP.
- Webhook authenticity and replay handling.
- Secret leakage in logs, errors, source maps, or client bundles.

Commerce and payments

Test:

- Client-side price manipulation.
- Negative or invalid quantities.
- Discount abuse.
- Stock races.
- Duplicate order submission.
- Duplicate or forged payment callbacks.
- Unauthorized order cancellation.
- Unauthorized refund operations.
- Payment status manipulation.
- Cross-tenant payment configuration access.
- Replay and idempotency behavior.

Tools and evidence

Use appropriate static analysis, dependency audits, secret scanning, automated tests, and controlled dynamic testing. Review findings manually.

Do not conduct destructive or unauthorized testing against third-party systems.

Create a security assessment report documenting:

- What was tested.
- Tools and versions used.
- Tests that passed and failed.
- Findings by severity.
- Evidence and reproduction steps for genuine findings.
- Fixes applied.
- Retests performed.
- Remaining risks and limitations.

Fix all confirmed critical and high-severity vulnerabilities before release. Address medium and low-severity issues according to their impact and document any that remain.

Do not claim that no vulnerabilities exist anywhere. No finite test suite can prove that. State precisely what was verified, what was not tested, and what remains uncertain.

22. Full-flow and regression testing

Test complete user journeys, not only individual components.

Merchant journey

Registration or invitation → verification → business creation → handle selection → template selection → branding → product creation → payment configuration → publishing → order receipt → order processing → fulfillment → reconciliation.

Customer journey

Visit storefront → browse products → select variants → cart → edit quantities → enter customer details → choose fulfillment → choose payment → submit order → receive reference → observe accurate payment and order status → access permitted order information.

Platform operator journey

Secure login → create or approve merchant → assign ownership → review domain and integration status → review Aevibron access request → manage merchant status → inspect audit history.

Security regression journey

Attempt cross-tenant access through each applicable route, API, query, upload, export, cache, and asynchronous workflow.

Additional quality checks

- Responsive mobile and desktop behavior.
- Accessible navigation and forms.
- Empty states and error recovery.
- Network failures and provider timeouts.
- Concurrent order and inventory operations.
- Database migrations from a clean database.
- Repeated order submissions.
- Webhook retries.
- CI and production build.
- Regression tests for existing working features.

Use integration and end-to-end testing tools appropriate to the chosen stack. Use isolated test environments and explicitly seeded test data where needed.

Test data must be clearly identified and isolated from live merchant data. Do not use a hardcoded demonstration backend to imitate production functionality.

23. Performance, observability, and reliability

Research and implement sensible production safeguards, including:

- Appropriate database indexes.
- Efficient pagination and queries.
- Bounded search operations.
- Safe caching with tenant-aware keys.
- Timeouts and retries for external services.
- Idempotent background processing.
- Rate limiting and abuse controls.
- Structured logs without secrets.
- Error monitoring.
- Operational health checks.
- Webhook and job diagnostics.
- Database backup and restoration procedures.
- Safe schema migration and rollback strategies.

Avoid speculative infrastructure and unnecessary microservices. Prefer a maintainable architecture that can evolve with real usage.

Never cache private responses across tenant or user boundaries.
